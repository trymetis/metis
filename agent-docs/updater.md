# Updater — the protocol, the Go updater and dashboard updates

How an instance moves to a newer published release and undoes the last upgrade: the ConnectRPC protocol in `proto/`, the Go updater in the `metis` CLI that implements it on a server, its database snapshots, and the dashboard that drives it.
Paths are from the repository root.
See also [AGENTS.md](../AGENTS.md), [deployment.md](deployment.md), [configuration.md](configuration.md), [dashboard.md](dashboard.md), [e2e.md](e2e.md).

## Rules

- **The app is the only client, and it calls the protocol and nothing else.** Whatever implements the protocol owns the containers.
- **The app reaches the updater over a Unix socket at `METIS_UPDATER_SOCKET`; whoever can open the socket may call it.**
  - Under systemd the socket is in `/run/metis-updater`, which the app bind-mounts read-only; in a container it is in the `metis-updater` volume, which the app mounts read-only.
  - Without the updater component the app gets no `METIS_UPDATER_SOCKET` and no mount.
- **The socket is mode `0600`, owned by the updater's user.** The updater and the app both run as root; a non-root app user would need ownership or a group with `0660`.
- **The updater installs only published releases newer than the running one.**
  - A release is a version whose app tag `:X.Y.Z` exists in `ghcr.io/trymetis/metis` (`fetchReleases`).
  - The repository is a constant, so a compromised app cannot make it run another image.
  - An older release is refused with `FailedPrecondition`, because its code may not read a schema a newer release migrated. While the running version is unknown any release may be chosen, and preflight refuses a database it cannot run on ([database.md](database.md)).
- **The only way back is Undo last upgrade, once.** It returns to the release that ran before the last successful upgrade and restores the database snapshot taken for it; afterwards there is nothing left to undo.
  - Undo discards every write since that upgrade, so the dashboard shows when the snapshot was taken, and the undo is audited ([audit.md](audit.md)).
- **A release needs the CLI version its `metis.json` names (`minCli`).** A newer release without a `metis.json` is not listed, and one whose `minCli` is above the running CLI is refused with `FailedPrecondition` and `MinCliMessage`, which tells the owner to run `sudo metis self-update`; the app shows it unchanged.
- **Snapshots exist only when the server runs sqld** (`StackBackend.Snapshots`: the `sqld` component is on and `DATABASE_URL=http://app.sqld:8080`).
  - With Turso or an external sqld the updater cannot copy the database, so an upgrade runs preflight against the live database while the app keeps serving, there is no undo, and the dashboard tells the owner to back up first.
- **The updater writes `app.version` and `app.images` in `metis.json`; nothing else moves the app** ([cli.md](cli.md)).
- **One upgrade or undo runs at a time on a server.** `Manager.Upgrade` and `Manager.Rollback` hold `metis.lock` for the whole run, so the daemon, a second daemon, `metis update` and every other mutating `metis` command exclude each other; `Manager.running` covers the same process.
  - A busy lock refuses at once with `Aborted`: "an upgrade or rollback is already running" when the record says so, otherwise "another metis command is changing this install".
- **Starting an upgrade or an undo takes TOTP** (`requireTotp`, scope `instance-update`), because both restart the app and an undo discards data.
- **The app passes the requesting user's id as `requested_by`**, which the updater keeps on the `Upgrade` record so the restored release can audit the undo; `metis update` and `metis undo` leave it empty, and `recordUndo` then audits the undo with no user and `via` `cli`.
- **With `METIS_UPDATER_SOCKET` unset there are no update controls**: the sidebar hides the entry, the page 404s and the procedures answer `NOT_FOUND` ([dashboard.md](dashboard.md)).
- **Generated code is never hand-edited.** Change `proto/`, then run `bun run proto:generate` from the root (buf with remote plugins pinned in `buf.gen.yaml`); oxlint and oxfmt skip `packages/updater-proto/src/gen`.
- **The Go import path comes from `buf.gen.yaml`, never from the proto file.** Its `M` option maps `updater.proto` to `apps/cli/gen`, so the file's `go_package` stays as published and the console's byte-for-byte copy keeps matching.
- **The TypeScript is generated with `erasable_syntax=true`**, which emits each proto enum as an `as const` object.
  - Workspace packages export source, so the web app's typecheck reads it under the web app's `erasableSyntaxOnly`, which rejects a TypeScript `enum`.
  - Each enum type includes `UnknownEnum` for values a newer peer sends, so the app maps enums with a `switch` and a `default`.
- **The e2e fake updater registers the generated Go handler with the Go updater's checks, order and messages.** A change to the protocol, the Go updater's errors or their messages updates `e2e/fakes/updater.go` in the same change ([e2e.md](e2e.md)).

## How it works

### The protocol

`metis.updater.v1.UpdaterService` (`updater.proto`), Connect protocol over HTTP/1.1 or h2c on the socket; all four procedures are unary. Versions are bare `X.Y.Z` strings with no `v`. An `Upgrade` record is what every write returns and what `GetUpgrade` reports.

- **Empty means none.** `current_version` is empty when the running images are not a release, `rollback_version` and `rollback_snapshot_at` when there is nothing to undo, a release's `notes` when its version folder has no `release.md`, and `GetUpgrade` returns no `upgrade` when none ever ran.
- **`snapshots`** says whether this install can snapshot its database; `rollback_version` is set only when it can and a snapshot is kept.
- **Errors are Connect codes**, returned by `manager.go` and `releases.go` and mapped by the app in `toOrpcError`.

- **The upgrade sequence.** `PULL` the target; `SNAPSHOT` (only with snapshots): stop the app, stop sqld, copy its volume, start sqld; `PREFLIGHT`, which migrates the database; `SWITCH` the app to the target; then `READY`: poll the app's `/api/readyz` until it answers 200 or the deadline passes.
- **The undo sequence** (`UPGRADE_KIND_ROLLBACK`). `PULL` the previous release; `RESTORE`: stop the app, stop sqld, replace its volume with the kept snapshot, start sqld; `SWITCH`; `READY`.
- **States.**
  - `RUNNING`, then `SUCCEEDED`.
  - `FAILED`: the previous release is serving, either because nothing was switched yet (a failed pull, snapshot, or preflight without snapshots) or because the switch was undone (`restored` true, after `RESTORE`, which also restored the snapshot when one was taken).
  - `ROLLBACK_FAILED`: the target failed and restoring the previous release failed too, or an undo failed after it touched the database, so the instance needs an operator. The error names the snapshot folder.
  - `step` is the step in progress while running and the step that failed afterwards; `error` explains it.
- **The undo target.** After a successful upgrade with a snapshot, `rollback_version` is the release that was running before it.
  - It is empty when the previous images were not a release, when no snapshot was kept or its folder is gone, and after an undo.
  - It is also empty once the last record is not that successful upgrade to the running release, so an undo never skips back over a release it did not install.

### The Go updater

- **Where it runs.** The `updater` component of the `metis` CLI ([cli.md](cli.md)):
  - `--systemd`: `/etc/systemd/system/metis-updater.service` runs `/usr/local/bin/metis updater serve`; `RuntimeDirectory=metis-updater` with `RuntimeDirectoryPreserve=yes` keeps `/run/metis-updater` across restarts, because the app's bind mount would otherwise point at a deleted folder.
  - `--docker`: the catalog's `updater` service, distroless with the host's `/usr/local/bin/metis` bound read-only, the Docker socket, the install directory at its host path and the `metis-updater` volume. It skips the `updater` component on every apply (`stack.Options.Keep`), so it never replaces itself mid-run.
  - In the CLI's own process: `metis update [VERSION] [--no-backup]` and `metis undo` run the same `Manager`, print each step, and ignore `SIGINT` and `SIGHUP` once the pull is done, saying the upgrade continues.
- **Settings.** The install directory comes from `/etc/metis/install-dir`, or `METIS_INSTALL_DIR` in the container; the socket, readiness timeout and release cache TTL come from `--socket`, `--ready-timeout` and `--releases-ttl`, or `METIS_UPDATER_SOCKET`, `METIS_UPDATER_READY_TIMEOUT` and `METIS_UPDATER_RELEASES_TTL`.
  - Readiness is `http://127.0.0.1:APP_PORT/api/readyz`, or `http://app:3000/api/readyz` in docker mode; `METIS_UPDATER_READY_URL` overrides it.
- **Releases** are read anonymously from the registry's tag list and cached for the TTL; a failed refresh keeps serving the last list.
- **Steps** (`StackBackend`).
  - `Pull` pulls the target's app, preflight and worker images.
  - `Preflight` runs the target's preflight image once (`stack.RunOnce`) with `.env`, so `metis.json` is untouched until preflight passes.
  - A snapshot stops `metis-sqld` and runs the sqld image once as `0:0` with the `metis-sqld` volume at `/var/lib/sqld` and `<install>/snapshots` at `/snapshot`, so the copy is consistent and needs no tool the sqld image lacks. It covers every namespace on that sqld.
  - An upgrade writes `snapshots/pending`; success promotes it to `current`, replacing the previous one, and a failed upgrade restores `pending` and deletes it, leaving `current` and its undo as they were. `--no-backup` takes none and drops `current`.
  - `Switch` writes the target's pins into `metis.json` under the held lock, then applies with every component but `app` and `worker` kept, so it recreates the app and every worker and leaves sqld, Caddy, the gateways and the updater untouched.
  - Restoring calls `Switch` with the previous images.
- **The record** lives in `metis.json` → `updater`: `previous` (the images before the last successful upgrade), `snapshotAt` and `last` (the `Upgrade` record as protojson).
  - Every step writes it under the lock; `Status` and `Last` read the file without the lock, because writes are atomic renames, so the dashboard also shows upgrades run from the terminal.
  - A record still `RUNNING` when `updater serve` starts with the lock free becomes `ROLLBACK_FAILED`, because the process died mid-upgrade.
- **Release notes and the minimum CLI** are `https://sh.trymetis.email/v<version>/release.md` and `metis.json`, fetched directly by version for each listed release newer than the running one (all while the running version is unknown).
  - A version's notes and `metis.json` never change, so fetched ones are kept for the life of the process; a version with none yet is asked again once per TTL.
  - The fetches share a 10 s budget per pass, and a failed one only leaves that release without notes or unlisted.

### The dashboard

- **Client.** `updates.ts` builds one connect-node transport over `nodeOptions.socketPath` with `httpVersion: "1.1"`; the socket path is boot config, so the client is a module constant. `toOrpcError` maps Connect codes to oRPC errors.
- **Status.** `dashboard.system.updates` calls `GetUpgrade` and then `GetStatus`, settling each on its own, so the last record still shows while the registry is unreachable. A release is `newer` only when the running version is known.
- **Releases.** Only newer releases are listed (all of them while the running version is unknown), each with Upgrade and its notes rendered with Streamdown.
- **Undo.** The Running release card has the one Undo last upgrade button, with the snapshot time; with no snapshot support it says so instead.
- **Auditing the undo.** `updatesStatus` calls `recordUndo`, which writes `instance.upgrade_undone` once per upgrade id after the restored release reports the undo as succeeded ([audit.md](audit.md)).
- **Progress.** The page polls every `POLL_MS` while a record is running and treats failed polls as the app restarting.

## Deliberate limits

- **Service definitions move with the CLI, never with an upgrade.** The updater moves only the app's three images; new container definitions, image pins and the updater itself arrive with `sudo metis self-update`, which restarts the updater and applies the new catalog ([cli.md](cli.md)).
- **Snapshots cover the `metis-sqld` volume only.** `sqld-resend` and the Resend gateway's volume are outside them; with `gateway-resend --database stack`, an undo rolls back the gateway's rows too.
- **One snapshot, one undo.** The snapshot costs a full copy of the sqld volume on the host and a short downtime on every upgrade; older states need the operator's own backups.
- **An undo is audited only once an instance role holder opens Updates on the restored release**, since nothing else runs `updatesStatus`.
  - So a `metis undo` on a server without the updater component, which has no Updates page, is never audited.
- **An undo replays scheduled work that already ran after the upgrade.** The snapshot holds the scheduled sends, snoozes, workflow triggers, events and waits as they were before the upgrade, so the runtime finds them due again on its first tick after the restore ([workflow-runtime.md](workflow-runtime.md)).
  - A scheduled message sent after the upgrade is sent a second time; nothing checks the provider for an earlier send.
  - A scheduled workflow that ran since then runs once more (missed slots collapse into one run), and a snooze whose time passed wakes again.
  - Changes already made at the providers (mail sent, labels, moves) are not reversed. The customer page `apps/docs/content/self-hosting/03-operate/02-upgrade-and-undo.mdx` warns operators.
- **No MCP tool reaches the updater.** The instance MCP tools cover the stats and System pages only ([mcp.md](mcp.md)).
- **The Go updater itself has no e2e coverage** (`e2e/E2E_MISSES.md`).
