# UI system — `@metis/ui`, shadcn, theme, shells and brand marks

How UI is built across the apps: the `packages/ui` shadcn layout, adding and styling components, theme and workspace brands, the mail shell, the source link and brand marks.
Paths are from the repository root; `src/…` means `apps/web/src/…`.
See also [AGENTS.md](../AGENTS.md), [shortcuts.md](shortcuts.md), [desktop.md](desktop.md), [mobile.md](mobile.md), [www.md](www.md).

## Rules

### Components

- **Always shadcn.** Before writing any interactive, overlay or layout UI, check `packages/ui/src/components/`.
  - If the component is missing, install it with `bunx shadcn@latest add <name>` from the consuming app; `base-nova` makes the CLI serve Base UI ports.
  - Style state-dependent variants with `cva` + `cn` as `button.tsx` does; colors come from tokens, never `style={{}}`.
  - Use the primitive for the job: `resizable` for drag-resize, `hover-card` for hover popups, `Button` for buttons.
  - A component missing from the repo is added through the CLI.
  - A bespoke component moves to its shadcn primitive when a change touches it; there is no bulk sweep.
- **Check `git diff` after every `shadcn add`.** The CLI can overwrite shared files that already exist (such as `button.tsx`) with upstream's version.
- **Generated primitives, `_components/` imports and the `cn` import follow [AGENTS.md](../AGENTS.md) §2 and §4.**
- **`cn` is shadcn's `cn` package, re-exported from `packages/ui/src/lib/utils.ts`.** Every `components.json` pins the `utils` alias to `@metis/ui/lib/utils`, so `shadcn add` writes its imports there.
- **A combobox chip's remove button must have a name.** The generated `ComboboxChip` renders an unnamed remove button, so removable chips use `RemovableChip` (`src/components/removable-chip.tsx`): the primitive with `showRemove={false}` plus a `ChipRemove` labeled "Remove <label>".
- **A `Sheet` sized by its own class sets it on the side variant** (`data-[side=bottom]:h-dvh`, `data-[side=left]:w-72`): the primitive's `data-[side=…]` sizes outrank a plain `h-*` or `w-*` class.
- **Text fields render the size their call site gives them; nothing forces 16px.**
  - iOS zooms into a focused field under 16px, so `src/app/layout.tsx` → `generateViewport` sends `maximumScale: 1` to iPhone, iPad and iPod user agents only; iOS still allows pinch zoom, and Android, which never zooms on focus, keeps pinch zoom untouched.
  - The generated `Input` and `Textarea` default to `text-base md:text-sm`, so every call site sets its own size (`text-[13px]` for forms, `text-sm` for chat composers).
- **Page titles use `PageHeader`** (`src/components/page-header.tsx`): the title with its action on one row and the description full width below, wrapping the action under the title only when the row runs out of room. Every settings, workspace-settings and dashboard page uses it; profile headers (an MCP client) keep their own layout.
- **The generated `CommandItem` always renders a trailing check icon**, invisible until the item is checked, and it keeps its width; search result rows hide it on phones (`src/components/search/result-row.tsx`).
- **Overlays are dialogs.** Anything that covers the page has `role="dialog"`, `aria-modal` and an accessible name: through the shadcn `Dialog`, or set explicitly on a bespoke shell.

### Brand and theme

- **`@metis/ui` is a brand-neutral component system; each app owns its brand.**
  - `tokens.css` holds only the neutral theme, the grayscale palette every page renders without a `data-brand`, and each app overrides it in its own CSS.
  - The web app's workspace themes are data, not CSS files: rows in the `theme` table, rendered to CSS per page (see Themes below).
  - The desktop renderer uses the neutral defaults as they are.
  - `apps/www` keeps its own components in `apps/www/src/components/ui/` ([www.md](www.md)).
- **Only workspace pages (`/w/[slug]/…`) carry a brand; every other page renders the neutral palette.**
  - Sign-in and the rest of `src/app/(auth)/`, `/native/*`, the dashboard, account settings, the MCP consent page and the maintenance page use the neutral theme.
  - `<html>` carries `data-brand` only on a workspace page, and every theme's CSS is keyed on that attribute, so `<html>` without it falls back to the neutral `:root` and `.dark` tokens.
  - The brand sits on `<html>`, never on a layout wrapper: Base UI portals (dialogs, menus, selects, popovers, tooltips) and the toaster render under `<body>`, outside any wrapper.
- **A scope that changes the palette redeclares the shadcn variables as well as the raw tokens.**
  - `--primary: var(--brand)` and the other mappings resolve where they are declared and descendants inherit the resolved color, so overriding `--brand` alone leaves `bg-primary` and `ring` on the outer palette.
  - The mapping block in `globals.css` is declared on `:root`, the element that carries `data-brand`, for this reason; a theme preview sets only raw tokens as inline style (`themeStyle`), so it uses `bg-brand`, `bg-panel` and the like, never `bg-primary`.
- **A theme is the 18 raw tokens of `THEME_TOKENS` for light and for dark, and nothing else.**
  - Every value must match `THEME_COLOR_PATTERN` (`#rrggbb`, `#rrggbbaa` or `rgba(r, g, b, a)`): `themePaletteSchema` checks it on every save and `themeCss` again when the CSS is built, so stored values can never carry `url()`, selectors or other CSS.
  - A theme never carries raw CSS: a workspace admin's theme runs for every member, and CSS could load remote URLs, read input values through selectors or hide the phishing warning.
- **Themes come from three places, all rows of `theme`.**
  - Built-in: `system_key` set, read-only, kept equal to `SYSTEM_THEMES` by preflight (`ensureSystemThemes`, one write at a time).
  - Every theme id is an opaque UUID; a built-in's is a constant in `SYSTEM_THEMES`, the same on every instance, and code finds built-ins by `system_key` (`systemTheme`), never by reading an id.
  - Instance library: `workspace_id` null and no `system_key`, edited on Dashboard → Themes by instance roles that operate.
  - Workspace custom: `workspace_id` set, edited by that workspace's owners and admins; it is deleted with the workspace.
  - A workspace may pick a theme only when the theme's `workspace_id` is null or its own (`findVisibleTheme`); the foreign key cannot express that, so the shared function checks it.
  - Names are unique per owner, case-insensitively, and an instance theme cannot reuse a built-in name: `theme_instance_name_idx` is a partial index, because SQLite treats every null as distinct in a plain unique index.
- **A workspace points at its theme (`workspace.theme_id`), so edits reach every workspace using it.**
  - The column is `NOT NULL` with Graphite's id as its default (`DEFAULT_THEME_ID`), so a new workspace starts on Graphite with no code path, and the foreign key's `ON DELETE SET DEFAULT` moves a deleted theme's workspaces to Graphite inside the database.
  - The default theme is fixed: changing it would take a migration, and `ensureSystemThemes` never removes a built-in that `SYSTEM_THEMES` still lists.
- **One builder serves the dashboard and the workspace settings** (`ThemeBuilderDialog`); the procedures behind it differ, so instance roles and workspace roles stay apart.
  - The accent color and the tint generate both palettes in OKLCH (`generatePalette`); Advanced edits any token, and regenerating replaces those edits.
  - `contrastIssues` warns, never blocks: text pairs aim for 4.5:1 and button text on the accent for 3:1.
  - The assistant and MCP create themes from an accent and a tint only (`createWorkspaceTheme`), through the same generator.
- **Every email the instance sends uses `MetisSuiteTemplate`, neutral black and white in Inter.**
- **Inter and JetBrains Mono cover Latin, Cyrillic, Greek and Vietnamese**, so names and subjects in those scripts render in the app's font instead of a system fallback.
  - JetBrains Mono's coding ligatures (`->`, `!=`, `==`) are off everywhere through `--font-mono--font-feature-settings` in `packages/ui/src/styles/globals.css`, because addresses and raw headers must show the characters as typed.
  - The font is served from the instance itself at `EMAIL_FONT_PATH` (no third-party request when an email opens), with `Access-Control-Allow-Origin: *` because webmail loads it cross-origin.
  - Gmail and Outlook for Windows ignore web fonts and fall back to the system stack; dark mode comes from `prefers-color-scheme` and Outlook.com's `[data-ogsc]`.

### Shells and the source link

- **`MailShell` is the mail surface's chrome, and only `m/[mailbox]/layout.tsx` mounts it.** It holds the folder sidebar, the resizable folders / main / agent panels, the compose dialog, message drag-and-drop, and the mail chords and help. The workflow builder, the assistant, calendar and drive bring their own shells.
- **Every search field is `SearchInput`** (`src/components/search-input.tsx`): a search icon and a clear button, in the mail list, the drive toolbar, the contacts filter, the MCP tool picker and the assistant rail.
- **An icon-only button gets its tooltip from `IconButton`** (`src/components/icon-button.tsx`), which also sets its `aria-label`.
- **Every account picker shows an account as Settings does** (`AccountOption` in `src/components/account-option.tsx`): the address or name, then the provider, server and account address, leaving out a part the name already holds (a calendar named "Google Calendar · …" or after its server), so two accounts on one server still differ by address, so one address connected twice (Gmail API and IMAP) can be told apart; `providerLabelFor` maps any resource and provider to its label.
  - Compose **From**, the signatures preview, **Try on recent mail** and the workflow resource pickers use it; the workflow directory carries each entry's `provider` and `server` for this.
- **An explanation of how something works sits behind an ⓘ (`InfoHint`, `src/components/info-hint.tsx`)**, which opens on click and on hover; status and error text, the consequence of an action and short data captions stay as visible text.
  - Dashboard sections take it as `Section` → `hint`, config cards as `ConfigCard` → `hint`.
- **Surface sidebars head their groups with `SidebarSection`** (`src/components/sidebar-section.tsx`): mail's Mailboxes and calendar's account groups, which pass `onToggle` to collapse.
- **The rail starts with a gear that opens workspace settings; the workspaces are the tiles lower on the rail** (`WorkspaceRailSwitcher`).
- **Every settings page is listed once, in `src/components/settings-nav.ts`.** Both settings sidebars, the rail's account menu and the search dialog's settings entries read it.
  - Workspace page slugs live apart in `src/workspace/settings-pages.ts` → `WORKSPACE_SETTINGS_PAGES`, the `page` type of `workspaceSettingsPath`; `NAV_COVERS_EVERY_PAGE` fails the build while a slug has no nav entry.
  - `settings-nav.ts` imports `lucide-react`, so nothing outside the UI imports it: `workspace/path.ts` reaches the workflow worker, which runs under `react-server` conditions where `createContext` does not exist.
- **On phones, a surface's aside is a sheet opened from the surface's own titlebar, never from the rail.**
  - `ResponsiveAside` (`src/components/mobile-aside.tsx`) turns the aside into a left `Sheet` below `48rem`; `MobileAsideTrigger` sits first in the surface's header and renders only while an aside is registered.
  - The headers that carry it: the mail list and the scheduled, snoozed and subscriptions views, `CalendarHeader`, `DriveToolbar`, the workflow editor's top bar and the assistant header.
  - `/settings`, `/w/[slug]/settings` and `/dashboard` follow the same pattern: their sidebar is the aside, and `MobileSectionBar` (`src/components/mobile-section-bar.tsx`) at the top of the page carries the trigger and the section name. `/settings` and `/dashboard` sit outside the `/w` layout, so their layouts mount their own `MobileAsideProvider`.
- **Every page shows an always-visible link to the source with the running version, outside any menu.**
  - AGPL §13 binds anyone who runs a modified version for network users to prominently offer its source, so the link ships in the product; the operator points it at their own source with `METIS_SOURCE_URL` ([configuration.md](configuration.md)).
  - A new surface with no rail or sidebar goes under `src/app/(auth)/` when it is signed out and `src/app/(standalone)/` when it is signed in; both layouts use `SourceFooterLayout`, which lays a transparent footer over the bottom of the page and pads the page's first element so a tall form never runs under it.
  - `/settings` and `/dashboard` put the full line at the bottom of their sidebar, and on phones, where the sidebar is a sheet, in `MobileSectionBar` beside the section name.
  - Every `/w/*` surface, including `/w/[slug]/settings`, shows a compact `GitBranch` icon and version at the bottom of the rail, which stays on screen on phones.
  - The icon is `GitBranch` because a fork's source may live on any host; the link points at the configured URL exactly as set.
  - The version is `apps/web/package.json` → `version` ([deployment.md](deployment.md)).

### Marks

- **Never hand-add, hand-edit or rename a file in `src/components/ui/svgs/`.** It is `bunx shadcn@latest add @svgl/<name>` output, run from `apps/web`; the registry picks the filename and casing (so `googleCalendar.tsx` sits beside `microsoft-outlook.tsx`), and a rename is rewritten back by the next add.
  - The svgl registry gives every file a fixed `target` of `components/ui/svgs/<name>.tsx`, which shadcn writes under the project's `src/` whatever the aliases say, so the marks live in `apps/web`, the only app that uses them.
  - A mark the registry does not carry (or a wrapped PNG/JPG) goes in `brand-marks.tsx`, with raster art in `apps/web/public/brand/`; every mark satisfies `BrandMark`.
- **The app's own mark is one drawing, and every copy is rendered from it**: two white triangles meeting at the centre, like a bow tie, on a square black 256×256 tile (`MetisMark` uses neutral-900 for the tile, inverted in dark).
  - Change the paths in `icon.svg` and every drawn copy in the code map, then re-render every rendered file with ImageMagick.
  - `favicon.ico` holds 48, 32 and 16 px.
  - `apple-icon.png` is 180 px, square and unrounded, because iOS rounds it.
  - `apps/desktop/static/icon.png` is 1024 px RGBA: the electron-builder `icon` for macOS and Windows, and the window icon.
  - `apps/desktop/icons/` is `linux.icon`: one file per size the hicolor theme declares, because GNOME looks icons up only in the size folders `index.theme` lists, which has no 1024.
  - `apps/desktop/static/trayTemplate.png` (18×18) and `trayTemplate@2x.png` (36×36) hold the triangles alone in black on transparency, cropped to them, because macOS draws a template image in the menu bar's own colour; only `setTray` on `darwin` uses them.
  - `apps/mobile/assets/icon.png` is square and opaque; `adaptive-icon.png` holds the triangles alone on transparency, at two thirds of their size in `icon.svg`, so they fill the 72dp visible area of the 108dp canvas over `#000000`.

## How it works

- **`packages/ui` follows shadcn's monorepo layout.**
  - `bunx shadcn@latest add <name>` run inside an app writes the primitive into `packages/ui/src/components/` and app-only blocks into the app.
  - Inside the package, files import themselves by package name (`@metis/ui/lib/utils`, Node self-reference).
  - The web app's and the desktop renderer's tsconfig map `@metis/ui/*` to `packages/ui/src/*` for the type checker; the mobile app uses its own primitives ([mobile.md](mobile.md)).
- **CSS layering.** The web app's and the desktop renderer's CSS start with `@import "@metis/ui/globals.css"`, which carries the tokens, the shadcn theme and an `@source` for the package's own files.
  - The web app adds its editor and preview styles after it.
  - The desktop renderer adds its fonts and an `@source` for its own pages.
  - The mobile shell has its own Uniwind `global.css` ([mobile.md](mobile.md)).
- **Light/dark.** next-themes sets the `.dark` class before paint (default `dark`), so there is no flash; Tailwind v4's `@custom-variant dark` keys off that class.
- **Workspace theme.** The root layout sets `data-brand` on `<html>` to the id of the URL's workspace's theme and renders that theme's CSS (`resolveActiveTheme`, `themeCss`) in a `<style href precedence>`, which React hoists into `<head>`.
  - The CSS is scoped by theme id (`html[data-brand="dd6487c8-2339-4f3c-8604-4178e640ab66"]` and its `html.dark` twin), so a style React leaves behind after navigation never applies to another theme, and an edited theme's newer style (its `href` carries `updated_at`) comes later and wins.
  - Its selectors outrank the neutral `:root` and `html.dark` tokens by specificity, whatever order the styles load in.
  - The root layout has no route params, so the proxy's `forward` passes the URL's workspace slug in the `BRAND_WORKSPACE_HEADER` request header; `brandHeaders` deletes any copy the client sent, on `forward` and on the not-found rewrite.
  - `resolveActiveTheme` renders no theme outside a workspace page, without a 2FA-verified session, for a workspace the user is not a member of, and in maintenance.
  - The root layout renders only on a full load or `router.refresh()`, so client navigation is handled by `WorkspaceBrand` in the `/w/[slug]` layout: it renders the same style, sets the attribute from that layout's workspace and removes it when the layout unmounts.
  - Both read the workspace and its theme through `getWorkspaceMembership` in `src/auth/session.ts` (`getWorkspaceBySlug` joins `theme`), which is cached per request, so a full load of a workspace page queries it once and needs no theme cache.
- **Page titles.** The root layout's `"%s • Metis Suite"` template titles every page, and `generateMetadata` in the mail, calendar and drive layouts names the resource (`src/workspace/titles.ts`).
