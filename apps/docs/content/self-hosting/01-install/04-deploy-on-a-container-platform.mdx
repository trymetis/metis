---
title: Deploy on a container platform
description: Run the published Metis Suite images on Railway, Render, Fly.io, Google Cloud Run, Kubernetes or any host that runs container images.
---

Use this page to run Metis Suite on a platform that runs container images, such as Railway, Render, Fly.io, Google Cloud Run or Kubernetes. You use the same published images as a server the `metis` CLI runs, but you start them yourself.

Without the `metis` CLI running your server, a few jobs become yours:

- You create the secrets and set every environment variable on the platform.
- You provide the two databases, for example on Turso.
- You run preflight once for every deploy, before the new version takes traffic.
- You choose how background work runs, if the platform stops idle containers.
- You upgrade by deploying a new version. The **Updates** page in the owner dashboard is not available.

## The images

All images are public, on `ghcr.io/trymetis/metis`. This page uses release `1.2.3` as an example. Use the release number you want instead.

| Image                                    | What it does                                                                                       | When you need it               |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------- | ------------------------------ |
| `ghcr.io/trymetis/metis:1.2.3`           | The app. It listens on port 3000.                                                                  | Always.                        |
| `ghcr.io/trymetis/metis:1.2.3-preflight` | Preflight: a one-time run that prepares the database for this version, then exits when it is done. | Once for every deploy.         |
| `ghcr.io/trymetis/metis:1.2.3-worker`    | The background worker.                                                                             | Only with the `bullmq` runner. |

Pin a release number. Do not use the `latest` tags, so that every image you run is the same version. Pre-releases have no `latest` tags. Releases are listed on the [Metis Suite releases page](https://github.com/trymetis/metis/releases), tagged `app-v` and the release number, such as `app-v1.2.3`.

Preflight runs only from the preflight image. The app image does not include it. So a "release command" or "pre-deploy command" that runs inside the app's own image cannot run preflight.

## Before you start

- **A platform** that can run a public container image, set environment variables, and run a one-off task with an image of your choice.
- **Two databases.** Use [Turso](https://turso.tech) for both: an app database and an AI memory database, each with its own URL and token. See [Create the databases on Turso](/self-hosting/reference/environment-variables#create-the-databases-on-turso). The app needs no disk of its own, so it does not matter if the platform wipes the container's files.
- **An `https://` address** for the app: the address the platform gives you, or your own domain pointed at the platform.
- **OpenSSL**, on your own computer, to generate the secrets.

You can also use a libSQL server (sqld) that you run yourself. The platform must be able to reach it over the network. Set `METIS_DB_DRIVER=sqld`. Both database URLs must start with `http://`, `https://`, `ws://` or `wss://`. Both tokens are required: `DATABASE_AUTH_TOKEN` and `MASTRA_DATABASE_AUTH_TOKEN`. Both databases must exist on the server before the first preflight. To make a matching key and token for it, run `metis sqld-auth` on any computer that has the `metis` CLI. It prints three lines: `SQLD_AUTH_JWT_KEY`, the key sqld checks tokens with, then `DATABASE_AUTH_TOKEN` and `MASTRA_DATABASE_AUTH_TOKEN`, which hold the same token. See [Use the metis CLI from your computer](#use-the-metis-cli-from-your-computer) and the [database variables](/self-hosting/reference/environment-variables#database).

Do not use the `local` database driver on a platform, even with a persistent volume. It is for development only.

<Steps>
  <Step title="Generate the secrets">
    Run this once for each of `BETTER_AUTH_SECRET`, `METIS_ENCRYPTION_KEY`
    and `METIS_DRIVE_RELAY_SECRET`:

    ```bash
    openssl rand -base64 32
    ```

    If you choose the `cron` runner in the next step, generate a
    `CRON_SECRET` the same way.

    For the setup code, use any random value of at least 8 characters.

    :::warning[Back up the encryption key]
    Copy `METIS_ENCRYPTION_KEY` to a safe place, such as a password
    manager. Without it, the stored passwords and tokens cannot be read,
    and every user has to reconnect every mailbox, calendar, drive and address book.
    :::

  </Step>

  <Step title="Choose how background work runs">
    Scheduled sends, snooze reminders and workflows run in the background.
    By default (`internal`), they run inside the app, so they need at least
    one app container that never stops.

    - **One container always running:** keep the default. On Google Cloud
      Run, also turn on CPU always allocated (instance-based billing). By
      default, Cloud Run gives a container CPU only while it handles a
      request, so background work may not run between requests.
    - **The platform stops idle containers** (for example Cloud Run with a
      minimum of zero instances, Fly.io machines that stop when idle, or a
      free tier that sleeps): use `cron` with an external scheduler, or
      `bullmq` with the worker image and your own Redis.

    The app cannot tell that a container platform stops idle containers,
    so it does not warn you. With `internal` there, background work stops
    whenever no container runs.

    Decide now. You set the choice as a starting value in the next step,
    and starting values are read only by the first preflight. You can
    change it later under **Dashboard**, **System**, **Workflow runner**.
    See [Background work](/self-hosting/configure/background-work).

  </Step>

  <Step title="Set the environment variables">
    Set the same variables on the app and on the preflight task. Write each
    value as it is, without quotes:

    ```bash
    BETTER_AUTH_URL=https://mail.example.com
    BETTER_AUTH_SECRET=your-first-generated-secret
    METIS_ENCRYPTION_KEY=your-second-generated-secret
    METIS_DRIVE_RELAY_SECRET=your-third-generated-secret
    METIS_DB_DRIVER=turso
    DATABASE_URL=libsql://metis-app-acme.turso.io
    DATABASE_AUTH_TOKEN=your-app-database-token
    MASTRA_DATABASE_URL=libsql://metis-memory-acme.turso.io
    MASTRA_DATABASE_AUTH_TOKEN=your-memory-database-token
    METIS_SETUP_CODE=K7QM-2HXP-9RTA
    METIS_OWNER_EMAIL=you@example.com
    ```

    Replace every example value with your own. Use the URL that
    `turso db show` prints for each database with `--url`, for example
    `turso db show metis-app --url`. It starts with `libsql://`.

    - **`BETTER_AUTH_URL`** is the one address people use. It must start
      with `https://`, which turns on secure sign-in cookies. Sign-in works
      only at this address, not at any other address the platform gives the
      same app.
    - **`METIS_SETUP_CODE`** opens the setup page for the owner account.
      Without it, the setup page shows **Not available**.
    - **`METIS_OWNER_EMAIL`** is the email of the owner, and it is required.
      Without it, preflight and the app do not start. Only this address can
      create the owner account on the setup page.
    - **`METIS_DRIVE_RELAY_SECRET`** is needed as soon as you list a WebDAV,
      FTP, FTPS, SFTP or relayed S3 server.

    If you chose `cron` or `bullmq`, add its variables too, for example:

    ```bash
    METIS_WORKFLOW_RUNNER_DRIVER=cron
    CRON_SECRET=your-cron-secret
    ```

    If you run more than one app container, also set the cache to `redis`
    or `upstash`, so that sign-outs and rate limits apply on every
    container. Sign-in works without it, because sessions are stored in the
    database. See the
    [cache variables](/self-hosting/reference/environment-variables#cache).

    Any other starting value, such as your OAuth providers or AI model,
    can go here too. See
    [Environment variables](/self-hosting/reference/environment-variables).

    :::note[Keep the image's NODE_OPTIONS flags]
    The app image sets `NODE_OPTIONS` to
    `--dns-result-order=ipv4first --no-network-family-autoselection`. A
    `NODE_OPTIONS` you set on the platform replaces it. If you need to set
    it, keep those two flags in it.
    :::

  </Step>

  <Step title="Run preflight">
    Run the preflight image once, as a one-off task, with the same
    variables as the app. It exits with success when it is done. Preflight
    must finish successfully before any app or worker of the new version
    starts. For example:

    - **Kubernetes:** a Job that runs before you roll out the app.
    - **Google Cloud Run:** a Cloud Run job.
    - **Any platform:** run the preflight image from your own computer or a
      CI job, wait for it to succeed, then deploy the app. The databases
      must be reachable from there.

      ```bash
      docker run --rm --env-file production.env ghcr.io/trymetis/metis:1.2.3-preflight
      ```

      `production.env` holds the same variables as the app, one
      `NAME=value` per line.

    A platform's own release or pre-deploy command works only if it runs
    the preflight image and the new version waits for it:

    - **Fly.io:** `release_command` runs in a temporary Machine made from
      the app's new image, so it cannot run preflight.
    - **Railway:** Railway says the pre-deploy command's dependencies must
      be installed in the application image. The app image does not include
      preflight, so the pre-deploy command cannot run it.
    - **Render and Heroku:** check in Render's
      [deploy guide](https://render.com/docs/deploys) or Heroku's
      [release phase guide](https://devcenter.heroku.com/articles/release-phase)
      which image the pre-deploy command or release phase runs. It must be
      the preflight image, and the new version must wait for it.

    Do not run preflight as a separate service that runs all the time next
    to the app. Nothing makes the app wait for it, a platform that restarts
    it after it exits runs it again and again, and several copies would
    change the database at the same time.

    Preflight applies the release's changes to the app database. The AI
    memory database sets itself up when the app first uses it. On the first
    run, preflight also stores your starting settings. Later runs store
    starting settings only for a new group of settings that a release adds
    to the dashboard, such as a new card. If a variable later differs from
    the stored setting, the stored setting is used, and preflight adds a
    warning in the **Environment differs from the stored config** group.
    Preflight then checks your servers, OAuth providers and AI model. A
    failed check only adds a warning under **Deploy checks** in the owner
    dashboard.

    Preflight fails when a variable is missing or wrong, when it cannot
    reach the database, when it cannot apply its changes, or when a newer
    release has already changed the database. Its log says why.

    Run preflight once for every deploy, not once for every container. In
    Kubernetes, use a Job before the rollout. Do not use an init container
    in each pod: several copies would then change the database at the same
    time. Running it again on the same version is safe.

    :::warning[Always run preflight before the app]
    If the app starts on a database that preflight never prepared, sign-in
    and the setup page fail with database errors. The readiness check
    `/api/readyz` still answers `200`, so your platform does not notice.
    :::

  </Step>

  <Step title="Deploy the app">
    Run the app image with these settings:

    | Setting      | Value                                                                                                                         |
    | ------------ | ----------------------------------------------------------------------------------------------------------------------------- |
    | Port         | `3000`. If the platform sets the `PORT` variable, the app listens on that port instead.                                       |
    | Address      | The app listens on all addresses (`HOSTNAME`, default `0.0.0.0`). Leave it as it is unless your platform needs another value. |
    | Health check | `/api/livez` to decide when to restart the app, and `/api/readyz` to decide when to send it traffic.                          |
    | Stop timeout | Long enough for open requests to finish. A server the `metis` CLI runs gives the app 30 seconds. See below.                               |
    | Disk         | None.                                                                                                                         |

    The platform handles HTTPS. `METIS_DOMAIN`, `APP_PORT` and Caddy belong
    to a server the `metis` CLI runs, so you do not need them. See
    [Health checks](/self-hosting/operate/health-checks).

    **Stop timeout.** The stop timeout is how long the platform waits
    between asking a container to stop and forcing it to stop.

    - **The app**, with the `internal` runner, does not wait for a running
      tick. It stops the tick and exits once open requests finish. The work
      that was cut off runs again shortly after, and a restarted app runs a
      tick when it starts. A send that was already leaving may need a
      person to check it. See
      [Check that it runs](/self-hosting/configure/background-work#check-that-it-runs).
    - **The worker**, with the `bullmq` runner, finishes the running tick
      first. Give it a stop timeout longer than **Tick budget (ms)**. 75
      seconds covers the default budget of 45 seconds. If you cannot raise
      the platform's limit that high, lower the budget under it.

    Some platform defaults are shorter than you may expect:

    | Platform         | Default                                                                                                                                                   |
    | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
    | Google Cloud Run | 10 seconds between `SIGTERM` and `SIGKILL`.                                                                                                               |
    | Fly.io           | `kill_timeout` is 5 seconds (at most 300), and `kill_signal` is `SIGINT`, not `SIGTERM`.                                                                  |
    | Railway          | `RAILWAY_DEPLOYMENT_DRAINING_SECONDS` is 0. Raise it in the service's settings.                                                                           |
    | Render           | 30 seconds. You can raise it to 300 with `maxShutdownDelaySeconds`.                                                                                       |
    | Heroku           | 30 seconds.                                                                                                                                               |

    See [Cloud Run](https://docs.cloud.google.com/run/docs/container-contract),
    [Fly.io](https://docs.fly.io/reference/configuration),
    [Railway](https://docs.railway.com/deployments/deployment-teardown),
    [Render](https://render.com/docs/deploys) and
    [Heroku](https://devcenter.heroku.com/articles/dyno-shutdown-behavior).

  </Step>

  <Step title="Start the background runner">
    Skip this step with `internal`.

    - **`cron`:** point a scheduler at the tick endpoint. See
      [cron](/self-hosting/configure/background-work#cron).
    - **`bullmq`:** run the worker image with the variables listed in
      [bullmq](/self-hosting/configure/background-work#bullmq), on the
      same version as the app. Give it a stop timeout longer than the tick
      budget (75 seconds is enough for the default).

  </Step>

  <Step title="Create the owner account">
    Open `/setup` at your address and use your `METIS_SETUP_CODE`. Continue
    with [First run](/self-hosting/install/first-run).

    Then open the owner dashboard and click the deploy check bar at the
    bottom of the sidebar to see any warnings from preflight. See
    [Owner dashboard](/self-hosting/operate/owner-dashboard#deploy-checks).

  </Step>
</Steps>

## What works differently

| Topic                  | On a container platform                                                                                                                                                                                                                                                                                                                            |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Upgrades               | The **Updates** page does not appear, because it needs the updater on a server the `metis` CLI runs. You upgrade by deploying a new version (see below).                                                                                                                                                                                           |
| Undo                   | There are no upgrade snapshots, so an upgrade cannot be undone. Back up your databases before every upgrade.                                                                                                                                                                                                                                       |
| HTTPS                  | The platform serves HTTPS. If you later change the address, update `BETTER_AUTH_URL` and register the new redirect URIs with your OAuth providers. See [OAuth providers](/self-hosting/configure/sign-in-providers). If **Public URL for webhooks and push** is not set, every webhook address changes too, so update the services that call them. |
| Relayed drives         | WebDAV, FTP, FTPS, SFTP and relayed S3 transfers work on a container that stays running. The **Transfers per user, per process** limit counts on each container separately. See [Drive transfers](/self-hosting/configure/drive-transfers).                                                                                                        |
| Several app copies     | Use a `redis` or `upstash` cache. Background work is never done twice.                                                                                                                                                                                                                                                                             |
| Your own changed build | If you run your own changed build, set `METIS_SOURCE_URL`. See [Source code link](/self-hosting/configure/source-code-link).                                                                                                                                                                                                                       |

## Visitor addresses behind the load balancer

Rate limits, sign-in limits and the IP addresses in the audit log use each visitor's address. So does the **Only from these IPs** setting of a webhook trigger. Behind your platform's load balancer, the app finds that address in the `X-Forwarded-For` header.

- **How the address is found.** The app takes the last entry of `X-Forwarded-For` that is not in a list of trusted proxies. Rate limits, sign-in limits and the audit log use **Trusted proxies** on the **Proxies** card, under **Dashboard**, **System**, **Instance**. The **Only from these IPs** check uses **Trusted proxies** under **Dashboard**, **System**, **Workflow runner**. See [Proxies](/self-hosting/reference/dashboard-settings#proxies).
- **What to list.** If your platform's load balancer adds the caller's address as the last entry, leave both lists empty. If another address follows the caller's in `X-Forwarded-For` (for example, a proxy behind the load balancer adds the load balancer's address), list that address in both. Your platform's documentation says how its load balancer sets `X-Forwarded-For`.
- **Ports are removed.** An entry with a port, such as `203.0.113.7:51234`, counts as `203.0.113.7`.
- **DigitalOcean App Platform hides the caller.** App Platform puts the address of its own ingress server in `X-Forwarded-For`, and the caller's address in a separate `do-connecting-ip` header. The app never reads `do-connecting-ip`, so it sees the ingress server's address instead of the caller's. Visitors who come through the same ingress server share one rate limit, and the audit log shows that server's address for them. Do not rely on **Only from these IPs** on App Platform. See DigitalOcean's [note on client IP addresses](https://docs.digitalocean.com/support/where-can-i-find-the-client-ip-address-of-a-request-connecting-to-my-app/).
- **Keep the app private.** Do not let callers reach the app without going through the load balancer. A caller who reaches the app directly can send any address in `X-Forwarded-For`. That address then counts for rate limits, sign-in limits, the audit log and **Only from these IPs**.

## Webhooks and push

Workflows can start from a webhook, or from a push message that Google Calendar, Google Drive or Microsoft sends when something changes. See [Webhooks and push](/self-hosting/configure/background-work#webhooks-and-push).

- **Public URL.** Webhook addresses use `BETTER_AUTH_URL`, unless you set **Public URL for webhooks and push** under **Dashboard**, **System**, **Workflow runner**. Push works only while that field is set. Without it, those triggers check for changes every few minutes. Enter an address that starts with `https://`.
- **Its variable is for new instances only.** Before the first preflight of a new instance, you can set the field's starting value with `METIS_WORKFLOW_PUBLIC_URL`. On an instance that already runs, the variable is not read, and it only adds a warning to the deploy checks. Set the field in the dashboard instead.
- **Only from these IPs.** This setting of a webhook trigger checks the caller's address, found as described in [Visitor addresses behind the load balancer](#visitor-addresses-behind-the-load-balancer).

## Use the metis CLI from your computer

The `metis` CLI also runs on your own computer, away from the platform. There it changes only outside services and an environment file you keep, such as `production.env` with the same variables as the app. To download it, see [Install the CLI on your computer](/self-hosting/reference/cli-commands#install-the-cli-on-your-computer).

Pass `--version` with the release your deployment runs, such as `1.2.3`.

- **Change dashboard settings**, such as an OAuth client, without opening the dashboard. The command updates the file, lists what to set on the platform, and stores the dashboard settings in the database once, through that release's preflight image:

  ```bash
  metis config set --env-file production.env --version 1.2.3 GOOGLE_CLIENT_ID=1234-abc.apps.googleusercontent.com GOOGLE_CLIENT_SECRET=your-client-secret
  ```

  The databases must be reachable from your computer. See [Change settings away from the server](/self-hosting/configure/how-configuration-works#change-settings-away-from-the-server).

- **Set up Google sign-in.** The file must contain `BETTER_AUTH_URL`. See [Set up Google with the metis CLI](/self-hosting/configure/sign-in-providers#set-up-google-with-the-metis-cli).

  ```bash
  metis connect google --env-file production.env --version 1.2.3
  ```

- **Set up a mail gateway.** For the Resend gateway, run the image `ghcr.io/trymetis/metis-gateway-resend:1.2.3` on your platform first, then set up the Resend side and print the gateway's values:

  ```bash
  metis add gateway-resend --endpoint https://resend-gateway.example.com --domain example.com
  ```

  The Cloudflare Email and Amazon SES gateways run on Cloudflare and AWS, so you set them up with `--remote`, for example `metis add gateway-cloudflare --remote --domain example.com --version 1.2.3`. See [Mail gateways](/self-hosting/mail-gateways).

- **Create mailbox tokens** on a gateway:

  ```bash
  metis gateway token create alice@example.com --endpoint https://resend-gateway.example.com --admin-token your-admin-token
  ```

:::danger[Never set METIS__UPDATER__FORCE_UPDATE_CONFIG_KEYS on the platform]
The CLI stores dashboard settings by passing `METIS__UPDATER__FORCE_UPDATE_CONFIG_KEYS` to one preflight run. Never set this variable yourself in the platform's environment. Every later preflight would then store those settings from the environment again, and overwrite what the owner or an admin changed in the dashboard.
:::

## Back up or move

The `metis` CLI on your computer can copy the whole instance into one encrypted file: both databases and the deployment's environment. You make a key once with `metis keygen`, then make the file with `metis db export --env-file production.env --recipient metis-export.pub` while the app is in maintenance. Later you can load it into two new, empty databases with `metis db load`, to restore the instance or move it to another platform or address. See [Export and import](/self-hosting/operate/export-and-import).

The owner sees every export under **Dashboard**, **System**, **Exports**. To send the file straight to a bucket, add `--out s3://example-backups/metis`. See [Upload to S3](/self-hosting/operate/export-and-import#upload-to-s3).

## Upgrade

<Steps>
  <Step title="Read the upgrade notes">
    Open the release on the
    [releases page](https://github.com/trymetis/metis/releases) and read
    its **Upgrade notes** section, if it has one. If you skip releases,
    read the notes of every release in between.
  </Step>

  <Step title="Back up both databases">
    Back up the app database and the AI memory database, and keep your
    encryption key with the backup. See
    [Backups](/self-hosting/operate/backups). To make one encrypted file
    of both databases and the environment, see
    [Export and import](/self-hosting/operate/export-and-import).

  </Step>

  <Step title="Run the new version's preflight">
    Run the new version's preflight image once, for example `ghcr.io/trymetis/metis:1.2.4-preflight`, with the same
    variables as before. Roll out the new version as soon as it succeeds.
    After preflight has changed the database, your current version may not
    work fully on it. For example, background work and the **Workflows**
    pages can stop working until the new version runs.

  </Step>

  <Step title="Roll out the new version">
    Change the app image to the new version, for example
    `ghcr.io/trymetis/metis:1.2.4`. If you run the worker, change it to the
    same version, such as `1.2.4-worker`, at the same time.
  </Step>
</Steps>

You cannot go back to an older release once a newer one has changed your database. Preflight refuses the database. Do not start the older app on it. To go back, restore the backup you took before the upgrade, together with the older release. See [Going back further](/self-hosting/operate/upgrade-and-undo#going-back-further).
