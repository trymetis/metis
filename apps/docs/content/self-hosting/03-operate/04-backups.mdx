Metis Suite has no built-in backup or restore. Back up the data below with the tools you already use for Docker volumes and files on your server.

On Metis Cloud, the Cloud service (not Metis Suite itself) backs up every running instance each night, keeps the two most recent backups and deletes them with the instance. The console has no button to restore them, so for a copy of your own, download an [export](/cloud/your-instance/export-your-data).

The updater keeps one copy of the database from before your last upgrade, so that you can undo it. That copy is not a backup. See [The upgrade snapshot is not a backup](#the-upgrade-snapshot-is-not-a-backup).

Most mail, events and files are not stored by Metis Suite at all. They stay with the provider or server each user connected, such as Gmail, Outlook or your IMAP server. Your instance keeps the accounts, the connections and their credentials, the settings, and what people create in the app.

Your instance also keeps a copy of the body of each message someone opened, until nobody has opened it for the number of days set on the **Mail cache** card (30 by default). It keeps the subjects, senders, AI labels, summaries and phishing check results of those messages too. See [Mail cache](/self-hosting/reference/dashboard-settings#mail-cache).

## What lives where

With the Compose stack installed in `/opt/metis-suite`:

| What                                        | Where                                  | Why it matters                                                                                                                                                               |
| ------------------------------------------- | -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The settings file, with every secret        | `/opt/metis-suite/.env`                | Holds the encryption key, the app secret, the database credentials and the release pins.                                                                                     |
| The app database and the AI memory database | The `metis_sqld` Docker volume         | Accounts, workspaces, connections, settings and their history, workflows, scheduled mail, the audit log, stored copies of opened message bodies, and the assistant's memory. |
| HTTPS certificates                          | The `metis_caddy_data` Docker volume   | Caddy gets a new certificate if this is lost, so it is optional.                                                                                                             |
| Updater state                               | `/opt/metis-suite/.updater-state.json` | The last upgrade or undo, the release you can undo back to, and when its snapshot was taken.                                                                                 |
| Upgrade snapshot                            | `/opt/metis-suite/.updater-snapshot/`  | The copy of both databases from before your last upgrade, used only by **Undo last upgrade**.                                                                                |

If your databases are on Turso, they live there instead of in the `metis_sqld` volume. The updater then takes no snapshot, so back them up before every upgrade.

:::warning[The encryption key and the database belong together]
The passwords and tokens in the database can be read only with the `METIS_ENCRYPTION_KEY` that was in use when they were stored. A database backup without its key is not enough to bring connections back: every user would have to reconnect every mailbox, calendar, drive and address book. Keep a copy of `.env`, or at least the key, with every database backup, and store it somewhere other than the server.
:::

## The upgrade snapshot is not a backup

When your instance uses the bundled database server, the updater copies the database before each upgrade from the dashboard. It keeps that copy so that you can [undo the last upgrade](/self-hosting/operate/upgrade-and-undo#undo-the-last-upgrade).

Do not rely on it as a backup:

- There is only one. Each successful upgrade replaces it, and an undo uses it up.
- It sits on the same server as the database, so it is lost with the server.
- It holds the database only, not `.env` and its encryption key.
- A bootstrap run takes no snapshot.
- With Turso or your own database server, there is no snapshot at all.

The folder holds a full copy of your database, so protect it as you protect the `metis_sqld` volume. It needs disk space: during an upgrade, the server can hold two copies at once. If you delete the folder, you lose the undo.

## Mailbox gateways

If you run a Cloudflare Email, Resend or Amazon SES gateway, it keeps its mail in its own storage, separate from your instance. Back it up there. For the Resend gateway, that is its libSQL database and its folder or S3-compatible storage. For the Amazon SES gateway, that is its libSQL database and its S3 bucket. See [Mail gateways](/self-hosting/mail-gateways).
