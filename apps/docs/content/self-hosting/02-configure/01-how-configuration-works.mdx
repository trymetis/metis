Metis Suite has two kinds of settings. Knowing which is which tells you where to make a change.

## Settings fixed at startup

These live only in the environment (the `.env` file) or in the optional config file. The app reads them when it starts, so a change needs a restart:

- The app address and its secret: `BETTER_AUTH_URL`, `BETTER_AUTH_SECRET`.
- The encryption key: `METIS_ENCRYPTION_KEY`.
- The first-run settings: `METIS_SETUP_CODE`, `METIS_OWNER_EMAIL`.
- The source code link: `METIS_SOURCE_URL`.
- How long the audit log keeps events: `METIS_AUDIT_RETENTION_DAYS`. It cannot be changed in the dashboard.
- The databases: `METIS_DB_DRIVER`, `DATABASE_URL`, `MASTRA_DATABASE_URL` and their tokens.
- The drive relay secret: `METIS_DRIVE_RELAY_SECRET`.
- Maintenance mode: `METIS_MAINTENANCE`. On a server the `metis` CLI runs, upgrades and undo turn maintenance on and off on their own. If you set it with `metis config set`, the app stays in maintenance, through every upgrade and undo, until you run `sudo metis config unset METIS_MAINTENANCE`. See [Maintenance mode](/self-hosting/reference/environment-variables#maintenance-mode).

On a server the `metis` CLI runs, change one with `metis config set`:

```bash
sudo metis config set METIS_SOURCE_URL=https://git.example.com/metis
```

The command writes the line to `/opt/metis-suite/.env`, shows what it changes, restarts the app on the new value (preflight runs first), and prints "Stored in /opt/metis-suite/.env and applied". To remove a variable, use `metis config unset`:

```bash
sudo metis config unset METIS_SOURCE_URL
```

You can also edit `/opt/metis-suite/.env` yourself, then apply it:

```bash
sudo metis apply
```

`metis apply` compares `.env` and the components with what runs, shows the changes and asks "Apply these changes?". `metis restart app` is not enough: it restarts the app as it is, without reading `.env` again.

On a container platform or Vercel, change the variable in the platform's settings and redeploy.

## Settings the owner or an admin changes in the dashboard

Everything else is stored in the database and changed by the owner or an admin under **Dashboard**, **System**:

- OAuth providers (Google, Microsoft and Zoho) and server lists.
- The AI model (LLM), the decision model and phishing detection.
- Outgoing email.
- The cache.
- The workflow runner.
- Sign-up, legal consent, drive transfer limits, the mail image proxy, the mail cache (how long message bodies are kept) and trusted proxies.

The first time preflight runs, it stores these settings. Each one takes its value from the environment or the config file if you set it there, and from its default otherwise. The defaults are: AI, the decision model and phishing detection off, outgoing email written to the server log, an in-memory cache, background work inside the app, invite-only sign-up, the mail image proxy off, message bodies kept for 30 days after they were last opened, no trusted proxies, and no providers.

When an update adds a new card to the dashboard, such as the decision model, the mail image proxy, **Mail cache** or **Proxies**, the next preflight stores it the same way, from the environment, the config file or the default. This happens on an instance that already runs too. **History** lists this as a **Seed** version.

Once preflight has stored a setting, the environment no longer changes it, unless you change it with the `metis` CLI (see [Change dashboard settings with the metis CLI](#change-dashboard-settings-with-the-metis-cli)). If a value in the environment later differs from the stored one, the stored value is used and the dashboard shows a warning under **Deploy checks**. Change the setting in the dashboard, or remove it from the environment. You can also click **Reset to environment** on the setting's card to apply the environment values again. The app reads the environment when it starts, so after you edit `.env` or the config file, apply the change as shown [above](#settings-fixed-at-startup) before you reset. See [Reset a card to the environment](/self-hosting/operate/owner-dashboard#reset-a-card-to-the-environment).

## Change dashboard settings with the metis CLI

`metis config set` and `metis config unset` also change dashboard settings. Among the variables you name, each one that belongs to a dashboard setting is stored in the database, over the value the dashboard holds. The others only go into `.env`. For example, this sets the Google OAuth client:

```bash
sudo metis config set GOOGLE_CLIENT_ID=1234-abc.apps.googleusercontent.com GOOGLE_CLIENT_SECRET=your-client-secret
```

- **The whole card is stored.** The command stores every field of each card a variable belongs to, from `.env` and the defaults. Another field of that card that you changed only in the dashboard goes back to its `.env` value or its default, as with **Reset to environment**.
- **A shared variable stores every card that uses it.** For example, `OPENAI_API_KEY` or `ANTHROPIC_API_KEY` can belong to more than one card.
- **`unset` returns a dashboard setting to its default.**
- **Server lists keep your dashboard entries.** On a server list, the command changes only the entries the CLI manages. See [Entries the metis CLI manages](/self-hosting/configure/server-lists#entries-the-metis-cli-manages).
- **History shows it.** The change appears under **System**, **History** as a **Server** version, by "Preflight", with the cards it changed.
- **Quote a value that holds spaces or JSON** in single quotes, so your shell passes it as one piece, for example `sudo metis config set 'METIS_IMAP_SERVERS=[{"name":"Office mail","imap":{"host":"imap.example.com"},"smtp":{"host":"smtp.example.com"}}]'`. The value is written to `.env` exactly as the shell passes it.

If a stored card fails its checks, preflight fails and nothing is stored in the database. The command shows "preflight failed:" with lines that name the card and the field, and the app keeps running. The change stays in `.env`, though. Fix the value and run `metis config set` or `metis config unset` again. A later `metis apply` alone starts the app on the new `.env` without storing the card, so the dashboard keeps its value and **Deploy checks** shows that the environment differs.

### Change settings away from the server

On a container platform or Vercel, run the CLI on your own computer with the deployment's environment file, such as `production.env` (one `NAME=value` per line, the same variables as the app). See [Install the CLI on your computer](/self-hosting/reference/cli-commands#install-the-cli-on-your-computer).

```bash
metis config set --env-file production.env --version 1.2.3 GOOGLE_CLIENT_ID=1234-abc.apps.googleusercontent.com GOOGLE_CLIENT_SECRET=your-client-secret
```

| Flag         | What it does                                                                                 |
| ------------ | -------------------------------------------------------------------------------------------- |
| `--env-file` | The deployment's environment file to update. Required away from the server.                  |
| `--version`  | The release the deployment runs, such as `1.2.3`. Needed when you change dashboard settings. |
| `--yes`      | Go ahead without asking.                                                                     |

The command:

1. Updates the file and prints "Updated production.env".
2. Prints "Set these on the platform that runs Metis:", followed by each `KEY=VALUE` to set and each `remove KEY` to remove. Make those changes on the platform.
3. Stores the dashboard settings among them once, in the deployment's database. With Docker running on your computer, it runs that release's preflight image once and prints, for example, "Stored GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET in the deployment's database". Your computer must be able to reach the databases.

Without Docker, it prints "Docker is not running here. Store the dashboard settings once with:" and a command such as this one. Run it once on a machine that has Docker and can reach the databases:

```bash
docker run --rm --env-file production.env -e METIS__UPDATER__FORCE_UPDATE_CONFIG_KEYS=GOOGLE_CLIENT_ID,GOOGLE_CLIENT_SECRET ghcr.io/trymetis/metis:1.2.3-preflight
```

If none of the variables is a dashboard setting, it prints "None of them is a dashboard setting, so the next deploy picks them up." Without `--version`, it updates the file, then stops with, for example, "GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET are dashboard settings; pass --version X.Y.Z, the release the deployment runs, to store them once through its preflight image".

:::danger[Never set METIS__UPDATER__FORCE_UPDATE_CONFIG_KEYS yourself]
The CLI passes this variable to one preflight run only. Never put it in `.env` or in a platform's environment, and above all never on a platform whose build or start command runs preflight on every deploy. Every later preflight would store those settings from the environment again, and overwrite what the owner or an admin changed in the dashboard. The CLI warns: "Never set METIS**UPDATER**FORCE_UPDATE_CONFIG_KEYS on the platform itself; every deploy would then overwrite the dashboard."
:::

## Saving a change in the dashboard

Each **System** page edits its own settings:

1. Change a field. A bar at the bottom shows how many changes are not saved yet, with **Reset** and **Save changes**.
2. Click **Save changes** and enter a code from your authenticator app. Backup codes work too.
3. The changed settings are checked against the real service before anything is stored. If a check fails, you see **Check failed** and "Nothing was saved. Fix the fields below and save again, or save anyway." See [Save anyway](#save-anyway).
4. If the check passes, you see "Saved as version N". The line at the top of the page says that every process picks up a change within 30 seconds.

Some values are refused before any check runs, for example a value that is not valid. Nothing is saved, and the error says why.

Every saved change becomes a new version of the configuration. So does every reset to the environment, which **History** lists as a **Reset** version. You can compare any two versions and restore an older one under **System**, **History**. See [Owner dashboard](/self-hosting/operate/owner-dashboard).

Secrets such as API keys and passwords are never shown again after you save them. The page shows **Set** or **Not set**. Leave a secret field empty to keep the stored value.

### What a save checks

A save checks only the cards you changed. Each check shows its result as **OK**, **Warning**, **Failed** or **Skipped**. A save is refused only when a result is **Failed**.

On a server list page, such as **IMAP** or **S3**, a save contacts only two kinds of entries:

- Entries you added.
- Entries whose connection settings you changed. Renaming an entry counts as a change. [Server lists](/self-hosting/configure/server-lists#what-a-save-checks) says which fields are connection settings for each provider.

The save does not contact the other entries. Each one gets one of these results instead:

- **Warning**, "Unchanged. The last deploy check reported: " followed by the problem, when the last deploy found a problem with that entry.
- **Skipped**, "Unchanged, so not checked again." This is the result in every other case.

Neither result can stop the save. So an entry you did not touch never blocks your change, and a save that only removes entries is never refused.

The **Warning** result repeats what the last deploy found. It is not a new test, so it can be out of date. It stops once you change the entry's connection settings and save, because that save checks the entry again. To test every entry now, click **Run check** in the page's **Health** card.

On the **Google**, **Microsoft** and **Zoho** pages, every field is a connection setting, so any change is checked.

Restoring a version under **History** and **Reset to environment** follow the same rules.

### Save anyway

When a check fails, the **Check failed** card has a **Save anyway** button. It stores your changes even though the check failed.

1. Click **Save anyway**. A dialog titled **Save anyway** says: "The check above failed. Saving anyway stores these changes as they are, so whatever failed the check may not work until it is fixed."
2. Enter a code from your authenticator app and click **Save anyway**.

You see "Saved as version N". **History** lists the version as an ordinary **Edit**.

**Save anyway** is on every **System** page whose cards run a check when you save: **LLM** (with the decision model), **Phishing detection**, **Mail**, **Cache**, **Workflow runner**, **Google**, **Microsoft**, **Zoho** and every server list page. It does not help with a value that is refused before any check runs. Fix that value first.

To store an older version whose check failed, use **Restore anyway** under **History**. See [History](/self-hosting/operate/owner-dashboard#history). **Reset to environment** has no such button.

### Warnings after a save

When a save succeeds, each **Warning** result appears as its own message. This also happens after **Save anyway**, a restore, **Restore anyway** and a reset to the environment. For a server entry, the message starts with the entry's name, then the check's name and the problem. For other settings, it starts with the check's name. For example, a model that your LLM provider does not list shows as "Models endpoint: not in the provider's model list:" followed by the model names.

When a save is refused, the warnings appear in the **Check failed** card instead, next to the failed results.

## The optional config file

Instead of environment variables, you can put settings in a YAML, JSON or TOML file. The app looks for, in order:

1. The file named in `METIS_CONFIG_PATH`. If that file does not exist, the app refuses to start.
2. `metis.config.yaml`, `.yml`, `.json` or `.toml` in the app's working folder.
3. `/etc/metis/config.yaml`, `.yml`, `.json` or `.toml`.

The file and the environment work key by key. When both set the same setting, the environment wins. An empty variable counts as not set.

The file uses nested sections instead of variable names. For example, this YAML file turns on open sign-up, sets the legal links, lists two trusted proxies and sets up outgoing email over SMTP:

```yaml
app:
  signupDisabled: false
legal:
  termsUrl: https://example.com/terms
  privacyUrl: https://example.com/privacy
proxies:
  trustedProxies:
    - 198.51.100.0/24
    - 2001:db8::/32
mailer:
  driver: smtp
  mailFrom: Metis Suite <noreply@example.com>
  host: smtp.example.com
  port: 465
  user: noreply@example.com
  pass: your-smtp-password
  secure: true
```

`trustedProxies` takes a list, as above, or one string with the entries separated by commas.

As with the environment, preflight reads the settings that the dashboard manages from the file only once, the first time it runs. After that, **Reset to environment** on a card applies the file's values to that card again, as the file was when the app last started.

:::note
A server the `metis` CLI runs gives the app no config file. Use `.env` there.
:::

## When a setting is wrong

The app checks every setting when it starts. A setting with a wrong value stops it from starting, and the error names the setting.

On a server the `metis` CLI runs, preflight runs before every new app starts. If it fails, the app that was running keeps running. The end of preflight's output is in the error of the command that made the change (`metis config set`, `metis apply`, `metis add`, `metis remove` or `metis domain`), after "preflight failed:". Fix the value and run the command again.

The app's own log shows errors after it has started:

```bash
sudo metis logs app
```
