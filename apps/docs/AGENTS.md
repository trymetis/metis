# apps/docs: Metis Suite customer docs (Blume)

The customer-facing documentation site, built with [Blume](https://blume.dev) (Astro and Vite underneath). It has two guides: the **User Guide** for people who use Metis Suite, and the **Self-Hosting Guide** for the operators who run an instance. Navigation, search and page metadata are inferred from the content files. Paths here are relative to `apps/docs/`. See also the root [AGENTS.md](../../AGENTS.md).

Blume owns the Astro layer: `content/`, `pages/` and `blume.config.ts` are the authored surface, and Blume generates its runtime under `.blume/` (gitignored). Its own docs ship in `node_modules/blume/docs/`; start at `index.mdx` and `01-quickstart.mdx`.

## Rules

- **Audience: customers.** Pages describe what a user or operator sees and does. Internal implementation, test fixtures and unbuilt work never appear; the `user-docs-only` skill holds the full list and the style rules (simple English, no emojis, no em or en dashes).
- **Content root is `content/`.** `NN-name` prefixes set sidebar order without changing URLs.
- **`.md` for prose, `.mdx` only when a page uses a Blume component** (`Steps`, `Card`, `CardGroup`, `Tabs`, `Accordion`) **or a `:::` callout**, which Blume renders only in `.mdx`. Components resolve without imports.
- **Frontmatter follows Blume's schema** (`node_modules/blume/docs/reference/frontmatter.mdx`).
- **Images are screenshots of the real app, never mockups.** Each one comes from an entry in `screenshots/<area>.json`; a page links only images that exist once the capture has run.
- **Every screenshot is linked as a light and dark pair, never as a Markdown image.** Blume has no themed content image, so a page writes two tags on consecutive lines, the same mechanism Blume's own logo uses: `<img src="/images/<name>.png" alt="…" class="dark:hidden" />` then `<img src="/images/<name>-dark.png" alt="…" class="hidden dark:block" />`. Blume's `dark:` variant follows its `data-theme` toggle, and both tags work in `.md` and `.mdx`.

## How it works

- **The docs agents run in order:** the feature finder reads the code and e2e specs for one area and reports what a customer sees; the writer turns that report into pages; the verifier checks every claim against the code, hunts for leaks and style violations, and runs `validate`.
- **Screenshots come from the e2e stack without its edge-case seed**, so test calendars, mail and files never appear.
  - `scripts/compose.screenshots.yml` also seeds the runner cadence at its documented default of 60 seconds, because the fixture's 2-second test cadence would show on every runner screen.
- **Capturing:** from `e2e/`, start it with `docker compose --env-file .env.fixture -f compose.yml -f ../apps/docs/scripts/compose.screenshots.yml up --build --wait app proxy`, then run `bun run screenshots` here (optionally with name prefixes, for example `bun run screenshots mail/`). The script runs every capture on the real clock, because files, saved chats, workflow runs and AI usage carry the time the stack was seeded or recorded; an entry with `"seededWeek": true` (the calendar views) freezes the browser clock at the seeded week instead (`DOCS_CLOCK`, default `2026-10-08T12:00:00Z`), since the calendar opens on today and has no date in its URL. It signs in as the seeded user through the harness, reads every `screenshots/*.json`, runs each entry's steps (`click`, `dblclick`, `rightClick`, `fill`, `type`, `press`, `hover`, `drag`, `waitFor`, `waitForHidden`, `wait`, `scroll`, `goto`, all with Playwright selectors; `type` clicks its selector and types `text` key by key, for editors such as the search box that `fill` cannot drive) and writes `public/images/<name>.png`. Path placeholders: `{workspace}`, `{mailbox}`, `{calendar}`, `{drive:<kind>}`.
  - `{ "drag": <from>, "to": <to> }` presses the mouse on one element and releases it on another in small moves, which is how a workflow step's output handle is wired to the next step; the palette adds steps unconnected.
  - `{ "waitForHidden": <selector> }` waits until a spinner or other transient element is gone, so a capture never shows a loading state.
- **Before every capture the script scrolls each `overflow: hidden` container back to its start.** The app shell is `h-dvh overflow-hidden`, and on a short viewport the rail is taller than the window, so focus or a click can scroll the shell itself and cut the top of the page; nothing a user can scroll is touched.
  - `{ "clearReadLater": true }` removes every Read later save of the seeded mailbox through the app's API before the next step: the recorded seed saves the shipment message under the id it has when the edge-case seed runs, and that id does not exist on this stack, so it would show as an unreadable row.
- **Each entry's steps run once and give both themes.** The script saves the light image, switches the app to dark in place (a `storage` event for next-themes' `theme` key) and saves `<name>-dark.png`, so an entry that changes data (marking read later, sending the approval chat) never runs twice.
- **What an entry captures:** the viewport by default (`fullPage` for the whole page); `clip`, a fixed region in page pixels; or `element`, one selector or a list whose boxes are joined, so a menu can be shot with the button that opened it. An element shot keeps a margin of page around it (`PAD`), and an element with a tall empty area below its last item is cut just under that item, so sidebars and panes do not come out as empty strips.

### Commands

- `bun run dev`: dev server with hot reload (port 4321)
- `bun run build`: static site to `dist/`
- `bun run typecheck`: `blume check`
- `bun run validate`: `blume validate --strict` (links, anchors and assets; safe beside a running dev server)
- `bun run screenshots`: refresh screenshots from a running e2e stack

`blume build` and `blume check` regenerate `.blume/`, so they conflict with a running `blume dev`; pass `--isolated` to run them alongside it.

## Deliberate limits

- **Screenshots are 1440 by 900 unless an entry sets a `viewport`.** Phone sizes are not captured.
- **The desktop and mobile apps have no screenshots**, because the e2e stack runs only the web app.
