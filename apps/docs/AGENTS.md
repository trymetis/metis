# apps/docs: Metis Suite customer docs (Blume)

The customer-facing documentation site, built with [Blume](https://blume.dev) (Astro and Vite underneath). It has three guides: the **User Guide** for people who use Metis Suite, the **Self-Hosting Guide** for the operators who run an instance, and **Metis Cloud** for customers of the hosted service. Navigation, search and page metadata are inferred from the content files. Paths here are relative to `apps/docs/`. See also the root [AGENTS.md](../../AGENTS.md).

Blume owns the Astro layer: `content/`, `pages/` and `blume.config.ts` are the authored surface, and Blume generates its runtime under `.blume/` (gitignored). Its own docs ship in `node_modules/blume/docs/`; start at `index.mdx` and `01-quickstart.mdx`.

## Rules

- **Every page has an audience level that sets which terms and behavior it may carry.** The `customer-docs` skill holds the levels and the pages each covers, what gets documented at all, what never appears, the style rules and how the docs agents are briefed.
- **Content root is `content/`.** `NN-name` prefixes set sidebar order without changing URLs.
- **The Metis Cloud tab documents the Metis Cloud console and what an owner sees inside a Cloud instance.** Each docs agent's prompt names the sources for the console; the instance is checked against this repository.
  - Cloud pages say only what differs on Cloud and link to the User Guide or the Self-Hosting Guide for the rest. The Self-Hosting Guide mentions Cloud only where Cloud changes a fact on the page, never as an advert; the User Guide never mentions it.
- **`.md` for prose, `.mdx` only when a page uses a Blume component** (`Steps`, `Card`, `CardGroup`, `Tabs`, `Accordion`) **or a `:::` callout**, which Blume renders only in `.mdx`. Components resolve without imports.
- **Frontmatter follows Blume's schema** (`node_modules/blume/docs/reference/frontmatter.mdx`).
- **Images are screenshots of the real app, never mockups.** Each one comes from an entry in `packages/screenshots/lists/pages/<area>.json` with `"target": "docs"` (or `"all"` when www shows the page too); a page links only images that exist once the capture has run.
- **Every screenshot is linked as a light and dark pair, never as a Markdown image.** Blume has no themed content image, so a page writes two tags on consecutive lines, the same mechanism Blume's own logo uses: `<img src="/images/<name>.webp" alt="…" class="dark:hidden" />` then `<img src="/images/<name>-dark.webp" alt="…" class="hidden dark:block" />`. Blume's `dark:` variant follows its `data-theme` toggle, and both tags work in `.md` and `.mdx`.

- **The changelog page has no content of its own: it shows the release files in the root `releases/` folder as written.**
  - A release appears on the next docs build after its file (such as `releases/app-v0.2.3.md`) lands; `## Unreleased` in the changelogs never shows.
  - The build reads the folder from the repository root, so the docs site builds from a full checkout; a missing folder or any file `@metis/releases` rejects (misnamed, frontmatter the schema refuses, no notes) fails the build.
  - Raw HTML in an entry is shown as text, so a placeholder written in angle brackets stays visible.
  - A bare email address stays plain text, since entries use example addresses; URLs and written Markdown links stay links.

## How it works

- **The docs agents run in order:** the feature finder reads the code and e2e specs for one area and reports what a customer sees; the writer turns that report into pages; the verifier checks every claim against the code, hunts for leaks and style violations, and runs `validate`.
- **Screenshots come from the e2e stack through `@metis/screenshots`**: the lists, steps, placeholders, Chrome flags, element boxes and terminal recording are in [screenshots.md](../../agent-docs/screenshots.md). This section covers what the docs capture adds.
  - After signing in, the script switches the seeded workspace from the e2e seed's Blue to the built-in **Graphite** theme, so every workspace screenshot matches the docs site's own Graphite palette.
- **A full capture needs both e2e stacks up at once:** run `bun run up:ss` in `e2e/` (the web stack with `packages/screenshots/compose.yml` over it) and `bun run up:ss` in `e2e-cli/` (the stack the `metis` CLI installs, on ports from 30050 up), then run `bun run screenshots` here (optionally with name prefixes, for example `bun run screenshots mail/`). It writes `public/images/<name>.webp`.
- **One run captures everything, in this order: the app-page entries from the web stack, then the terminal entries and the entries with `"maintenance": true` from the CLI stack.**
  - The maintenance entries are taken signed out at the CLI stack's app (`DOCS_CLI_APP_URL`, default `http://localhost:30050`) while it is frozen the way an operator freezes it: the last terminal entry runs `metis config set METIS_MAINTENANCE=2026-11-11T10:00:00Z` on `cli-host` (the script runs it itself when that entry is filtered out), and the run ends with `metis config unset METIS_MAINTENANCE`.
- **The terminal entries run on the CLI stack's `cli-host` and give both themes.** The script starts ttyd there through `docker compose exec` and opens it through `localhost:30054`.
  - The session is root's own shell in `/root` with the usual `root@metis-server:~#` prompt in color, so every command is shown the way an operator signed in as root types it, with no `sudo`.
  - `"prompt": "user@local-machine"` on an entry draws that name and a `$` instead, for a command the pages tell the reader to run on their own computer (`metis keygen`); the session still runs on `cli-host`, so only the label differs.
  - `{current}`, `{next}`, `{cli}` and the other release names from `e2e-cli/lib/releases.ts` are replaced in `type`, `answer`, `waitFor` and `hidden`.
  - **The terminal entries need only the CLI stack**: `bun run screenshots self-hosting/terminal` runs with the web stack down, and so does `self-hosting/maintenance-page`, because the script asks the web harness for the seeded account only when an app-page entry is in the run.
  - The sequence runs top to bottom on `cli-host` after the app-page entries: its first entry wipes the CLI stack's install and takes `metis keygen` with no install on the machine, the next installs a fresh one through `bootstrap`, and the rest work on that install.
- **An entry with `"invite"` captures the invite page from a real emailed link.** The stack sends mail to the harness's console endpoint (the fixture's console mail driver), so before the entry the script signs in as the seeded owner, sends a workspace invite into the seeded workspace (`"workspace": true`) or an account invite (optional `"role"`), reads the link from `/console-mail-hits` (`sentInviteLink` in `e2e/lib/invites.ts`) and substitutes it for `{invite}` in `path`.
  - `"email": "{member}"` is the seeded second account, so a signed-out entry shows **Sign in to accept**; any other address shows the sign-up form.
  - Any pending invite to that address is revoked before and after the capture, so no other screenshot shows it in a pending list.
- **An entry with `"observer": true` is captured as an Observer.** The script makes the seeded second account an Observer through the Users page's API, signs in as it with the code from its enrollment, captures, then removes the role again.
- **Before every capture the script scrolls each `overflow: hidden` container back to its start.** The app shell is `h-dvh overflow-hidden`, and on a short viewport the rail is taller than the window, so focus or a click can scroll the shell itself and cut the top of the page; nothing a user can scroll is touched.
- **Each entry's steps run once and give both themes.** The script saves the light image, switches the app to dark in place (a `storage` event for next-themes' `theme` key, and `prefers-color-scheme: dark` for pages that follow the device, such as View original) and saves `<name>-dark.webp`, so an entry that changes data (marking read later, sending the approval chat) never runs twice.
  - The init script that starts each page light writes `theme` only in the top frame. The email frame is same-origin and reloads its `srcDoc` when the theme changes, so a write from inside it would reset the shared `localStorage` to light and turn the whole app back before the dark capture.
- **What an entry captures:** the viewport by default (`fullPage` for the whole page); `clip`, a fixed region in page pixels; or `element`, one selector or a list whose boxes are joined. An element shot keeps a margin of page around it (`PAD`, or the entry's `pad`).

### Commands

- `bun run dev`: dev server with hot reload (port 4321)
- `bun run build`: static site to `dist/`
- `bun run typecheck`: `blume check`
- `bun run validate`: `blume validate --strict` (links, anchors and assets; safe beside a running dev server)
- `bun run screenshots`: refresh screenshots from the two running e2e stacks

`blume build` and `blume check` regenerate `.blume/`, so they conflict with a running `blume dev`; pass `--isolated` to run them alongside it.

## Deliberate limits

- **Screenshots are 1440 by 900 unless an entry sets a `viewport`.** Phone sizes are not captured.
- **Terminal screenshots are only as fresh as the stack's releases**: the versions they show are the CLI stack's (`apps/web/package.json` and the next ones built from it).
- **The desktop and mobile apps have no screenshots**, because the e2e stack runs only the web app.
- **The Metis Cloud pages have no screenshots.**
